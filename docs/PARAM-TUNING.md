# 参数调优：按机器环境与用途调整

**中文** | [English](PARAM-TUNING.en.md)


> 供 AI agent 在部署时**根据用户机器的真实情况**决定 llama.cpp 参数，
> 而不是照抄默认值。文中所有数字来自 RTX 3070 8GB 实测，**公式与决策逻辑可迁移到其他硬件**。

---

## 1. 调优前先测三件事（不要猜）

```bash
# ① 显存（MiB）—— 决定上下文上限
nvidia-smi --query-gpu=name,memory.total --format=csv,noheader,nounits

# ② 内存（GB）—— 决定能否用 -nkvo / 更长上下文
free -g | awk '/^Mem:/{print $2}'

# ③ CPU 核心数 —— 决定 -t
nproc
```

**把这三个数字写下来**，后面的决策全靠它们。

---

## 2. 显存预算公式（先算，再设 `-c`）

8GB 卡的实际分配（实测，RTX 3070）：

| 项目 | 占用 |
|---|---|
| 模型权重（PTQ1_0） | **≈ 5.53 GiB** |
| CUDA 上下文 + 计算缓冲 | **≈ 0.5 GiB** |
| KV cache | 见下公式 |
| **可用给 KV 的余量** | **≈ 2.2 GiB** |

### KV cache 大小公式

本模型：**64 层 = 16 层全注意力 + 48 层线性注意力**，`n_kv_heads=4`，`head_dim=256`。

```
KV_bytes ≈ 2 × n_kv_heads × head_dim × 每元素字节 × 全注意力层数 × ctx
         = 2 × 4 × 256 × 每元素字节 × 16 × ctx
         = 32768 × (每元素字节) × ctx
```

| KV 量化 | 每元素字节 | 化简后 | 100K 时 |
|---|---|---|---|
| `f16` | 2 | `65536 × ctx` | 6.25 GiB |
| **`q4_0`** | **0.5625** | `18432 × ctx` | **1.76 GiB** |

> ⚠️ 实测 128K + q4_0 时引擎申请 **2304 MiB**（比理论值大），说明还有对齐/开销。
> **以 `cudaMalloc` 报错里的 `allocating X MiB` 为准**。

### 推论

```bash
# 8GB 卡
可用给 KV ≈ 2.2 GiB
q4_0 时最大 ctx ≈ 2.2 GiB / 18432 ≈ 125K  ← 理论
实测上限 = 102400（106496 就 OOM）        ← 实测（有额外开销）
```

**结论：不要用理论值设上限，要实测逼近**（见 §6）。

## 3. 参数速查表

| 参数 | 作用 | 默认 | 怎么调 | 何时调 |
|---|---|---|---|---|
| `-ngl N` | 放 GPU 的层数 | 0 | **99 = 全部上卡**；放不下就降 | 显存 < 模型大小 |
| `-c N` | 上下文长度 | 4096 | 按 §2 算 + §6 实测逼近 | 总是要调 |
| `-fa on` | Flash Attention | auto | **必须显式 `on`** | 总是 |
| `-ctk` / `-ctv` | K / V 缓存量化 | f16 | **两者必须相同** | 上下文 > 32K 时改 q4_0 |
| `--parallel N` | 并发槽位 | 4 | **设 1** | server 模式、上下文 > 32K 时**必须** |
| `-t N` | CPU 线程 | 自动 | GPU 跑满时**无影响** | 仅 `-ngl 0` 纯 CPU 时有意义 |
| `-b` / `-ub` | 逻辑/物理批大小 | 2048/512 | 实测 256–1024 无显著差异 | 一般不用调 |
| `-nkvo` | KV 放系统内存 | off | 需要超长上下文时开 | 显存不够放 KV 时 |
| `--jinja` | 用模型自带 chat 模板 | off | **必须开** | 总是 |
| `--chat-template-kwargs` | 传模板参数 | — | `{"reasoning_effort":"medium"}` | 推理模型必需 |

## 4. 三个"必须成对/一致"的约束（违反会出问题）

### 4.1 K 和 V 的量化类型必须相同

实测（同一模型、同一上下文）：

| K / V | 生成速度 | 预填充 |
|---|---|---|
| `q4_0` / `q4_0` | **51.7 t/s** | 888 t/s |
| `f16` / `f16` | 52.3 t/s | 894 t/s |
| **`q4_0` / `f16`** | **40.9 t/s** ❌ | **303 t/s** ❌ |
| **`f16` / `q4_0`** | **40.8 t/s** ❌ | **240 t/s** ❌ |

**混用会让速度和预填充同时暴跌。**

### 4.2 `-parallel` 与上下文长度的关系

`llama-server` 会为**每个 slot** 分配 `rs cache`（线性注意力层的循环状态）。
默认 `--parallel 4` 时，**100K 上下文会启动失败**：

```
failed to allocate buffer for rs cache
```

**规则**：
- `-c` ≤ 32768 → `--parallel` 可用默认值，但设 1 更省内存
- `-c` > 32768 → **必须 `--parallel 1`**

> 这也是「`llama-cli` 能吃 100K 而 `llama-server` 不行」的原因 —— server 多了 slot 开销。

### 4.3 `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 必须等于服务端 `-c`

```
可用 prompt 预算 = n_ctx − CLAUDE_CODE_MAX_OUTPUT_TOKENS
```

例：`102400 − 16384 = 86016`。两者不一致会导致：
- 声明过大 → 请求超出服务端上限
- 声明过小 → 上下文浪费

## 5. 按机器分档的推荐配置

### 显存分档

| 显存 | `-ngl` | `-c` | KV | 生成速度（实测/推算） |
|---|---|---|---|---|
| **8 GB** | 99 | **102400** | q4_0 | ~39 t/s |
| 10 GB | 99 | 131072 | q4_0 | ~35 t/s |
| 12 GB | 99 | 196608 | q4_0 | ~30 t/s |
| 16 GB | 99 | **262144**（原生上限） | q4_0 | ~30 t/s |
| 6 GB | 99 | 65536 | q4_0 | ~40 t/s |
| **< 6 GB** | 降 `-ngl` | 按剩余显存 | q4_0 | 显著下降 |

> 上表的 `-c` 是**全 GPU 上限**。若要超过，见 §5.3。

### 5.1 内存分档（影响 `-nkvo` 能否用）

| 内存 | 可用的最长上下文（`-nkvo`） | 说明 |
|---|---|---|
| 8 GB | 不做 `-nkvo` | 模型 + KV 挤不下 |
| 16 GB | ≤ 131072 | KV(q4_0) 约 2.3 GiB |
| **48 GB** | **262144** | 实测通过 |
| 64 GB+ | 262144 | |

### 5.2 CPU 分档（只影响 `-ngl` < 99 时的 CPU 部分）

| 核心数 | 说明 |
|---|---|
| ≥ 8 | `-t 8` 即可（GPU 是瓶颈） |
| 4–8 | `-t $(nproc)` |
| < 4 | 不要降 `-ngl`，纯 CPU 会非常慢 |

### 5.3 要超过全 GPU 上限时：三种方案实测对比

以 8GB 卡跑 128K 为例：

| 方案 | 上下文 | 生成速度 | 评价 |
|---|---|---|---|
| `-ngl 58 -c 131072`（6 层放 CPU） | 128K | **7.5 t/s** | ❌ 不推荐 |
| **`-ngl 99 -nkvo -c 131072`**（KV 放内存） | 128K | **6.7 t/s** | |
| **`-ngl 99 -nkvo -c 262144`** | **262K** | **10.9 t/s** | ✅ **要开就开满** |

> ⚠️ **关键发现**：`-nkvo` 下 128K 和 262K 速度**几乎一样**（瓶颈在 PCIe 传 KV，
> 不在长度）。所以**要么不开 `-nkvo`，要开就直接开到模型原生上限**。

## 6. 实测调优流程（用 llama-bench 逼近真实上限）

**不要凭公式设上下文上限** —— 直接测。

### 6.1 找上下文上限（二分法）

```bash
LLAMA=./llama.cpp/build/bin/llama-cli
MODEL=./models/Ternary-Bonsai-2-27B-PTQ1_0.gguf
export LD_LIBRARY_PATH=./llama.cpp/build/bin

# 反复试，找到"通过"与"OOM"的边界
$LLAMA -m $MODEL -ngl 99 -c 131072 --parallel 1 -fa on -ctk q4_0 -ctv q4_0 \
       -n 8 --no-warmup -st -p "hi" < /dev/null 2>&1 \
  | grep -oE "allocating [0-9.]+ MiB|out of memory|Generation: [0-9.]+ t/s"
```

- 出现 `Generation: xx t/s` → 通过
- 出现 `allocating X MiB ... out of memory` → 超过上限，**把 `-c` 减半再试**，逼近边界

> **报错里的 `allocating X MiB` 就是 KV 实际要的显存**，用它反推上限最准。

### 6.2 测不同上下文的生成速度

```bash
./llama.cpp/build/bin/llama-bench -m $MODEL \
  -ngl 99 -fa 1 -ctk q4_0 -ctv q4_0 -ub 512 -t 8 \
  -d 0,16384,32768,65536 -n 128 -r 2 -p 0
```

`-d` 是上下文深度。实测曲线（8GB 卡）：

| 深度 | 生成速度 |
|---|---|
| 0 | 51.5 t/s |
| 16K | 42.5 t/s |
| 32K | 35.7 t/s |
| 64K | 26.7 t/s |

**向用户说明这个衰减**，让他知道"上下文越长越慢"是正常的。

### 6.3 验证参数是否已饱和（省得白调）

实测结论 —— **以下参数在本类模型上"调了也没用"**：

| 参数 | 实测差异 | 结论 |
|---|---|---|
| `-t 4/6/8` | 51.67 / 51.61 / 51.52 | 无差异（GPU 瓶颈） |
| `-ub 256/512/1024` | 差异 < 1% | 不用调 |
| `GGML_CUDA_FORCE_MMQ=1` | 无提升 | 不用加 |

**这是显存带宽瓶颈的模型，别过度调参。**

## 7. 按用途分档的推荐预设

| 用途 | 上下文 | 关键参数 | 理由 |
|---|---|---|---|
| **接入 Claude Code** | **102400** | `--parallel 1`，`MAX_OUTPUT_TOKENS=16384` | Agent 任务频繁多轮，**速度比超长上下文重要** |
| 通用对话 | 32768 | 默认 | 平衡 |
| 长文档问答 | 131072 | `-nkvo` | 接受速度下降 |
| 超长上下文（整本书） | 262144 | `-nkvo` | 速度与 128K 相同，不亏 |
| 最快响应 | 4096 | 默认 | 51 t/s |

### 7.1 Claude Code 场景的额外调优

```bash
# 服务端：推理模型必须给足输出预算
-n 16384                # 太小会得到空回答（思考吃光预算）
--reasoning-effort medium   # 默认 xhigh 太啰嗦

# Claude Code 侧（写进 settings.json）
"CLAUDE_CODE_MAX_CONTEXT_TOKENS": "102400",   # = 服务端 -c
"CLAUDE_CODE_MAX_OUTPUT_TOKENS": "16384"      # 与服务端配合
```

**`-n` 太小是最常见的"模型坏了"误判**：只看到 thinking 没有结论，
其实是思考用完了额度。**先怀疑额度，再怀疑模型。**

---

## 8. 调优后要做的两件事

### 8.1 回写到脚本

把测出来的最优值写进 `scripts/start-bonsai.sh` 的对应位置：

```bash
CTX=${CTX:-<你测出的上限>}          # 如 102400
# 启动参数里的 -c "$CTX" --parallel 1 保持不变
```

或在运行时覆盖：
```bash
CTX=131072 ./scripts/start-bonsai.sh restart
```

### 8.2 告知用户

| 要说的 | 为什么 |
|---|---|
| 测出的上下文上限 | 用户会想知道"能开多大" |
| 速度随上下文的衰减曲线 | 避免用户以为"变慢了是坏了" |
| `-n` 与 `reasoning_effort` 的关系 | 避免误判"模型不输出" |
| 是否用了 `-nkvo` 及其速度代价 | 让用户在"长上下文 vs 速度"间有知情选择 |

## 9. 快速自检清单

调参完成后逐项确认：

- [ ] `-fa on` 已显式指定
- [ ] `-ctk` 与 `-ctv` **完全相同**
- [ ] `-c` > 32768 时，`--parallel 1` 已设
- [ ] `-c` 是**实测**出的值，不是公式推算
- [ ] `-n` ≥ 16384（推理模型）
- [ ] `--chat-template-kwargs` 里 `reasoning_effort` 已设
- [ ] `CLAUDE_CODE_MAX_CONTEXT_TOKENS` == 服务端 `-c`
- [ ] 启动后 `nvidia-smi` 显存占用合理（无残留、未爆）
- [ ] 用 `llama-bench` 记下了实际速度，并已告知用户
